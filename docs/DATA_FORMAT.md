# Подготовленный набор данных v1

Команда `python -m tram.cli publish <каталог>` читает `manifest.json` и `observations.jsonl`. Она не изменяет входные файлы и не обучает модель. Готовый пример создаётся командой `python -m tram.cli demo data/demo`.

## manifest.json

Обязательные поля верхнего уровня:

| Поле | Содержимое |
| --- | --- |
| `capabilities` | Объект `Capabilities` из OpenAPI: версия набора/сети, режим источника, профили истории и прогноза. |
| `network` | `{ "id": "версия-сети", "routes": [RouteDetail, ...] }`. Даты действия, направления, позиции остановок и сегменты проверяются на согласованность. |
| `sources` | Массив `SourceStatus`. Режим всех источников совпадает с режимом набора. |
| `models` | Массив `{ "profile_ids": ["профиль-прогноза"], "model": ModelReference }`. Поддерживается только `seasonal_naive_v1`, `is_baseline=true`. |
| `series` | Массив объявлений рядов, описанных ниже. |

Объявление ряда содержит ровно `profile_id`, `spatial`, `geometry`, `coverage_start`, `coverage_end`. `profile_id` указывает на профиль **наблюдений**; `spatial` соответствует `SpatialKey`, `geometry` — `Geometry` или `null`. Покрытие — полуинтервал в пределах истории профиля. Геометрия остановки — Point, остальные уровни — LineString/MultiLineString. Различные позиции одной остановки различаются `stop_sequence`.

Метрика, единица, пространственный уровень, шаг и агрегация связанного профиля прогноза должны совпадать с наблюдениями. Доступные горизонты: `day/hour`, `month/day`, `year/month`. Профили объявляют реальные допустимые даты. Для годового горизонта начало — первое число месяца; для остальных — местная полночь. Все календарные правила используют Europe/Moscow.

Для сезонной базы `training_history_end` — зафиксированная граница истории манифеста, а не свидетельство выполненного обучения. Модель с границей позже `as_of` не выбирается. Калиброванные интервалы не заявляются (`prediction_interval_available=false`).

## observations.jsonl

Одна запись на строку:

```json
{"profile_id":"validations-route-hour","available_at":"2026-09-20T11:05:00+03:00","point":{"spatial":{"level":"route","route_id":"route-1","direction_id":null,"stop_id":null,"stop_sequence":null,"segment_id":null},"interval_start":"2026-09-20T10:00:00+03:00","interval_end":"2026-09-20T11:00:00+03:00","value":120,"missing_reason":null,"value_kind":"observed","estimation_method":null,"quality":{"status":"ok","coverage_ratio":1,"flags":[]}}}
```

`point` проверяется как `ObservationPoint` из OpenAPI. `available_at` — когда этот агрегат стал известен системе; он не раньше конца интервала и не позже публикации. Исправленный позднее агрегат получает время фактической доступности исправления. Прогнозы не используют его до этого момента.

В каждом ряду записи идут строго по времени и полностью покрывают объявленный диапазон. Ряды можно чередовать, но порядок внутри ряда обязателен. Дубликаты, пропущенные строки и неполные интервалы отклоняются. Отсутствие наблюдения представляется строкой с `value=null`, непустым `missing_reason` и соответствующим качеством. Нулевое наблюдение передаётся числом `0`.

Для оценки факта используются `value_kind=estimated` и непустой `estimation_method`. Число валидаций само по себе не подтверждает посадки, заполненность или вместимость; подготовка таких показателей требует отдельной обоснованной методики.

План такой методики описан в [PASSENGER_OCCUPANCY.md](PASSENGER_OCCUPANCY.md): группы посадки, оценки высадок и постоянный остаток по вагону/рейсу, затем агрегирование по участкам. Её выход можно публиковать в текущем формате как `estimated` после реализации и проверки конвейера. Состояние групп, сырые ответы погоды/событий и реестр источников не добавляются произвольными полями в `manifest.json`: действующий импорт отклоняет неизвестные поля. Для них планируются отдельное внутреннее хранение и версионированные адаптеры; см. [DATA_SOURCES.md](DATA_SOURCES.md).

## Атомарность и неизменяемость

Валидатор читает JSONL последовательно, SQL-адаптер вставляет наблюдения пакетами по 500 строк. Проверка полноты выполняется внутри транзакции: ошибка даже в последней строке откатывает сеть, набор, ряды и наблюдения. Поддерживается импорт подготовленных агрегатов; сырые миллионы событий сначала требуют отдельного ETL.

Версии сети и набора неизменяемы. SHA-256 охватывает канонический JSON манифеста и последовательность записей. Повтор тех же данных с тем же порядком строк безопасен; другие данные или другой порядок требуют нового ID версии. PostgreSQL сериализует конкурентную публикацию одной версии. Имена и содержимое исходных файлов в БД не переписываются.

При появлении новых данных публикуется новый набор; неизменённая сеть может использовать прежний ID. Геометрия хранится в GeoJSON; геопространственные запросы PostGIS пока не реализованы. Отчёты backtesting не входят в этот формат: их рассчитывает и публикует отдельная команда evaluate.


## Дополнительные адаптеры

`prepare-csv` создаёт этот же формат из агрегатов CSV; `export-occupancy` — из журналов посещения остановок. `publish` выполняет общую атомарную проверку. Гео/погодные/событийные снимки хранятся отдельно и не добавляют произвольные поля в manifest.json. Отчёты оценки создаются командой evaluate. Подробные команды: [OPERATIONS.md](OPERATIONS.md).
