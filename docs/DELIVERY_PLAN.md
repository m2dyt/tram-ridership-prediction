# Полная итерация без обучения

Запрос: довести доступные части проекта до рабочего состояния и оформить документацию по папкам. Модели не обучаются. Реальные пассажирские данные и недоступные учётные записи не заменяются вымышленными.

## Порядок

1. Проверка репозитория/окружения, фиксация архитектурных границ.
2. Баланс пассажирских групп: чистое ядро, три сценария, SQL-состояние, события, идемпотентность и восстановление; API и тесты.
3. Источники: погодные/событийные адаптеры, импорт городской географии, сохранение версий и ошибок; признаки с ограничением as_of.
4. Backtesting сезонной базы без fit: полные горизонты, метрики и атомарная публикация отчётов в существующий API; подготовка CSV-агрегатов.
5. React/JavaScript/Vite/Leaflet: карта, прогнозы, история/оценка, состояние вагонов и внешних источников; проверка сборки и пользовательских сценариев.
6. Воспроизводимый запуск, проверки, документация каждой папки и назначение файлов, корневой README и навигация.
7. Итоговое ревью и сквозная проверка; отдельно зафиксировать внешние ограничения.

Перед реализацией каждого шага — конкретный план в сообщении; после — проверка и ревью в журнале. Изменения API сопровождаются обновлением OpenAPI. Внешние зависимости остаются во внешних слоях; domain/application/ML не импортируют HTTP/SQL/React.

## Итог реализации

Шаги 1–5 выполнены и проверены; добавлены калькулятор выпуска и экспорт наполненности в estimated-наблюдения. Документация слоёв, назначение каждого файла, инструкции запуска и карта файлов созданы. Заключительные проверки фиксируются в [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md), внешние границы — в [STATUS.md](STATUS.md). Требования, зависящие от реальной схемы/доступа или обучения, не объявляются выполненными.

Шаги 6–7 завершены: инструкции/карта файлов проверены, итоговый полный прогон и реальные HTTP-сценарии прошли. Контейнерная сборка ограничена доступом к PyPI; точный результат внесён в журнал.
