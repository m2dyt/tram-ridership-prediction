# Очередь задач: модель, данные и backend

Этот файл — рабочий checklist после анализа в [HACKATHON_READINESS_PLAN.md](HACKATHON_READINESS_PLAN.md). Задачи ограничены источниками данных, моделью, обучением, inference API, проверкой качества и документацией запуска. Frontend не рассматривается.

Сначала закрывать задачи по порядку. Каждая задача заканчивается коротким review: проверить предпосылки, найти утечки/неверные нули, сверить метрики и обновить документы. Не переходить к сложной модели, если не закрыт контракт данных или baseline.

## Какой код должен появиться в результате

Это план реализации, а не backlog одних проверок. Аудит нужен как входные требования к следующему коду; результат каждого крупного этапа — работающий файл, команда или endpoint.

1. **Загрузчик и контракт конкурса.** Добавить команду подготовки архива, которая читает исходные `train.csv`/`test.csv`/sample, проверяет схему, типы, ключи и версию словаря; нормализует route/date/hour к одному внутреннему формату; пишет отчёт качества, `manifest.json` с SHA-256 и воспроизводимую матрицу train/validation. Исходный ZIP не изменяется. Предлагаемые места: `scripts/prepare_tram_challenge.py`, `ml/training/tram_data.py`, `data/training/tram-competition-v1/`.
2. **Функции признаков вместо одного большого скрипта.** Разделить `train_tram.py` на импортируемые блоки: временной/calendar feature builder, историю и сезонный профиль, прогноз baseline, обучаемый estimator, обучение/evaluate folds, форматирование submission. Старый CLI оставить тонкой оболочкой до сравнения результата. Предлагаемые файлы: `ml/training/tram/features.py`, `baseline.py`, `models.py`, `evaluation.py`, `submission.py`, `cli.py`.
3. **Реальный модельный эксперимент.** Добавить конфиг эксперимента с целевой колонкой, временными отсечками, признаками, seed и параметрами; научить CLI выдавать baseline и минимум два обучаемых кандидата — регуляризованную линейную модель и градиентный бустинг. Подбирать параметры только на rolling-origin validation. Сохранять out-of-fold прогнозы, общую/per-route/per-hour метрики, coverage и ablation отчёт. Не принимать вручную заданные route коэффициенты без такого сравнения.
4. **Рабочие внешние feature pipelines.** Написать отдельные загрузку/нормализацию для исторической погоды и таблицу календаря; сохранять сырые ответы в `sources/`, подготовленные таблицы в `data/`, версии/параметры/хеши в provenance. Weather join выполняется по `valid_at` и для live режима дополнительно ограничивается `issued_at <= as_of`. Календарь содержит обычный weekday/weekend, официальный рабочий день, праздник, перенос, предпраздничный признак. Трафик и мероприятия получают тот же adapter pattern, только если найден пригодный архив.
5. **Неизменяемый model bundle и команды.** Создать `train`, `evaluate`, `export` команды, которые отдельно запускаются из shell/worker job. Bundle хранит сериализованный estimator, feature schema, config, splits, метрики, input/code/dependency hashes и model card. Экспорт пишет новую версию, не перезаписывает текущую; loader отклоняет несовместимую схему или checksum.
6. **Инференс в FastAPI worker.** Реализовать инфраструктурный `ArtifactPredictor`, который адаптирует bundle к текущему порту `Predictor`, и настроить `composition.py` выбирать модель по конфигурации. API не содержит fit; `SeasonalNaive` остаётся включаемым fallback. В API metadata добавить идентификатор/версию модели и время `as_of`; выполнить endpoint и worker integration проверку на одной и той же feature transform, что использовалась при обучении.
7. **Единая эксплуатация.** Унести `catboost`/`lightgbm`, если они нужны выбранному кандидату, в `pyproject.toml` optional extra; сохранить один основной `requirements.txt`, обновить CLI docs, Docker/compose только для backend нужд, и добавить реальный performance benchmark. GPU не является требованием к прогнозу или установке.

Пути файлов здесь — предлагаемые deliverables. Если аудит покажет уже существующий модуль с тем же назначением, расширить его вместо создания дубликата и обновить таблицу ответственности.

## Порядок следующего инженерного шага

1. **DATA-01:** сверить платформу и зафиксировать лучший текущий результат. Это защищает от случайной потери рабочего варианта перед дедлайном.
2. **DATA-02–03:** сначала подтвердить содержание/качество конкурсного архива и смысл меток; не менять алгоритм по одному score.
3. **MODEL-01–04:** закрепить baseline и сделать аудит текущих конкурсных поправок/временной валидации.
4. **DATA-04–05 и MODEL-05:** включить погодный архив и официальный календарь только с ablation. Это наиболее выполнимые дополнительные источники.
5. **DATA-06:** выяснить наличие реального исторического трафика и событий; пока доступа/архива нет, не блокировать модель на этом.
6. **BACKEND-01–06:** только после утверждения feature/model contract подключить готовый обученный артефакт к worker/API.
7. **DOC-01:** синхронизировать инструкции со сделанным и записать финальную review/проверки.

## Определение готовности одной задачи

Перед изменением записать короткий план из 3–6 пунктов. После реализации выполнить review с рисками/пограничными случаями, затем релевантные unit/API checks; для изменения модели сохранить прогнозы, конфиг, split и метрики. Не запускать обучение на финальном test и не считать network/API HTTP 200 доказательством пригодного датасета. Обновить README/документ конкретной папки. После этого зафиксировать изменение отдельным осмысленным commit; не переписывать историю и не отправлять результат на площадку без отдельного запроса.
