# От исходных данных до обученной модели

> **Актуальность:** это историческая техническая справка по подготовке и квартальному metro pipeline. Она не является отдельным актуальным планом. Очередь всех работ находится в [единственном глобальном плане проекта](../00_ГЛОБАЛЬНЫЙ_ПЛАН_К_ЭТАЛОНУ.md).

Этот документ остаётся планом доведения данных метро и общего ML слоя. В репозитории есть конфигурируемые `prepare.py`, `train.py`, `evaluate.py` и реализация квартальных признаков/оценки; наличие файлов не означает, что каждая конфигурация/модель проверена на актуальном окружении. Сборка backend worker пока использует сезонный Predictor. Обучение не выполняется при запуске API.

Каждый шаг вести в порядке **план → выполнение → ревью → исправления**. В ревью сохранять проверенные файлы, фактические результаты и оставшиеся ограничения; журнал проекта — [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md).

**Уже сделано для метро:** скачаны 624 v6.8 и 62743 v1.35, выполнен [первичный аудит](DATA_AUDIT.md), реализованы подготовка, временные splits и сезонная база — [METRO_PIPELINE.md](METRO_PIPELINE.md). Результат: 315 рядов за 22 квартала, 6 930 точек плотной сетки; 193 нуля сохранены, пять внутренних и 477 внешних пропусков обозначены явно. Признаки и обучающая выборка ещё не созданы. Следующая работа — проверить причины проблем и 16 географических несовпадений, согласовать переименования и признаки. ID сейчас относится к точной паре названий, не к постоянной физической станции.

## Шаг 1. Выбрать одну постановку

План:

1. Проверить полученные файлы по [реестру датасетов](DATASETS.md).
2. Зафиксировать единицу прогноза, показатель, частоту, горизонт и момент выдачи `as_of`.
3. Определить, чем проверять результат, и какие сведения были доступны на дату прогноза.

| Вариант | Целевой ряд | Откуда | Граница применимости |
|---|---|---|---|
| Учебный эксперимент метро | Станция × квартал × один показатель потока с единицей из паспорта | Набор **62743** пользователя | Отдельный эксперимент; не прогноз по трамваям. Сначала проверить фактическую схему и длину истории. |
| Первый трамвайный прогноз | Например, маршрут/направление × час × число посадок | Реальные валидации или согласованные агрегаты | Посадки не равны одновременной наполненности. |
| Наполненность | Участок направления × час × среднее число пассажиров или доля вместимости | Измерения либо баланс рейсов с пометкой `estimated` | Нужны привязка к вагонам, проезды, выходы/сценарий и вместимости для ratio. |

Рекомендация для первого трамвайного эксперимента: один маршрут, сутки вперёд, почасовые значения. Это ограничение первого эксперимента, не обещание достаточности любого объёма данных. Для квартального метро нужна история нескольких сезонных циклов; если её недостаточно для раздельных train/validation/test, результат ограничить разведочным анализом и базой.

**Результат:** описание задачи в `data/training/<версия>/task.md` (будущий файл). **Ревью:** показатель имеет физический смысл; метки метро не названы трамвайными; горизонт соответствует частоте и данным.

## Шаг 2. Сохранить оригиналы и подготовить целевой ряд

План:

1. Сохранить оригиналы и паспорт в [sources](../sources/README.md), не редактировать их при очистке.
2. Реализовать преобразование фактической схемы поставщика, сформировать словарь колонок и отчёт качества.
3. Сопоставить ID и версии сети, обработать дубли/пропуски и агрегировать только в допустимую частоту.

Для 62743 проверить единицы и семантику значения, квартал, направление потока и ID станции. После соединения с 624 сверить число строк и суммы: несколько входов одной станции не должны дублировать её поток. Не интерполировать кварталы до суток/часов для оценки точности.

Для трамваев разнести `event_time`, период агрегирования и `available_at`. Пропуск — не ноль. Закрытая остановка, отменённый рейс и ошибка датчика — разные причины. Исправления исходников оформлять новой ревизией; проверять пространственные связи и границы действия сети.

Для наполненности применяется баланс `после = до + вошли − вышли`. Остаток хранится по вагону/рейсу и переносится на следующий участок. Минимальная длительность ограничена следующей остановкой, максимальная — конечной; распределение между ними является допущением. Сравнить сценарии короткой, равномерной и длинной поездки. Полученная таким способом наполненность — **оценка**, а не наблюдение. Подробности: [PASSENGER_OCCUPANCY.md](PASSENGER_OCCUPANCY.md).

Для агрегатов наполненности использовать вес времени проезда каждого вагона; долю вместимости сначала считать по вагону. Нельзя складывать средние значения как число уникальных пассажиров. Для обучения на восстановленных метках нужен отдельный отчёт о точности восстановления по независимым подсчётам. Без них модель обучается воспроизводить сценарную оценку, а не доказывает точность реальной наполненности.

**Результат:** нормализованный целевой ряд, словарь полей и отчёт в [data](../data/README.md). **Ревью:** дубли, полнота, единицы, нули/пропуски, время, provenance и источник меток проверены. Исходные файлы сохранили SHA-256.

## Шаг 3. Зафиксировать временную проверку до обучения

План:

1. Выделить раннюю часть истории под обучение, последующий период под выбор модели, самый поздний — под финальный тест.
2. Задать несколько последовательных отсечек с **полными** горизонтами и достаточной предысторией. Даты выбрать после аудита покрытия, не из произвольного примера.
3. Зафиксировать правила переобучения и доступности целевых меток на каждом fold.

В train входят только строки, у которых целевой интервал завершился и метка уже доступна на отсечке обучения. Для многошаговых меток удалить или отделить зазором строки, чей target пересекается с validation/test. Разделение делать по времени **сразу для всех станций/маршрутов**, а не случайным перемешиванием строк. Преобразователи, импутация и выбор признаков обучаются только внутри train соответствующего fold.

Финальный test не участвует в выборе признаков, гиперпараметров и порогов принятия. Если после его просмотра поменяли модель, для нового независимого заключения нужен новый отложенный период. Неполный год нельзя оценить как полный годовой прогноз. Длина истории оценивается по сезонным циклам, пропускам и стабильности результатов, а не только числу строк.

**Результат:** для метро уже сохранён `data/metro-evaluation/seasonal-20260922/splits.json`: train 2021–2023, validation 2024, test 2025-Q1…2026-Q2. Для будущего обучающего процесса — `data/training/<версия>/splits.json` с датами и правилами. **Ревью:** границы не пересекаются, но историческая доступность московского релиза не доказана; текущий эксперимент помечен retrospective_snapshot. Варианты модели должны использовать одинаковый протокол. Просмотренный test нельзя использовать для подбора решений и затем выдавать за независимую проверку.

## Шаг 4. Построить признаки и посчитать базу

План:

1. Начать с календаря и прошлых значений целевого ряда.
2. Собрать одну общую спецификацию признаков для обучения и прогнозирования.
3. Получить сезонный прогноз и сохранить ошибки на тех же отсечках, где будет проверяться модель.

| Признак | Как получать | Что проверить |
|---|---|---|
| Час, день недели, месяц, выходной | `tram_ml/features.py`, календарь Москвы | `is_weekend` сейчас означает субботу/воскресенье, не официальный календарь праздников и переносов. |
| Лаги и скользящие статистики | Из завершённой и доступной на `as_of` истории | Использовать сдвиг до агрегирования; будущие целевые значения недоступны. |
| Маршрут, направление, остановка/участок | Согласованные версии сети и ID | Новые/переименованные объекты, неизвестные категории, период действия. |
| Расстояние до метро/POI | 624 либо проверенный геоисточник + `tram_ml/context.py` | География могла измениться; расстояние по прямой не равно времени пешего пути. |
| Погода | Снимок прогноза, доступный на отсечке, с нужным временем действия | Фактическая будущая погода недопустима; текущие адаптеры не создают исторический архив выпусков. |
| Мероприятия | Версия анонса, известная до прогноза | Пагинация, переносы, пропуски координат; количество событий не равно посещаемости. |

При выдаче сразу 24 часов фактическое `y` первого часа ещё неизвестно для расчёта второго. Выбрать явную стратегию: отдельные модели/признаки для каждого шага, общая модель с признаком lead time либо рекурсивный прогноз. При рекурсии используются предыдущие **предсказания**, а не будущие факты. Это же правило действует при backtesting. Погодный прогноз на три дня не покрывает месяц/год.

Для поддерживаемых опубликованных трамвайных профилей база уже доступна:

```powershell
python -m tram.cli evaluate --help
```

Полностью рабочие команды с синтетическим набором — в [OPERATIONS.md](OPERATIONS.md). Сейчас `EvaluateBaseline` заполняет `model` и `seasonal_naive` одной сезонной базой. Для квартального метро реализован отдельный `evaluate-metro`: «тот же квартал прошлого года», один квартал вперёд с последовательными отсечками. Более ранний факт из test может использоваться только в прогнозе более позднего квартала; это не многоквартальный прогноз из одной даты. [Протокол, команды и метрики](METRO_PIPELINE.md).

**Результат:** отчёт квартальной базы уже есть в `data/metro-evaluation/seasonal-20260922/`; спецификация `features.json` и обучающие признаки — следующая работа. **Ревью:** каждая будущая колонка должна иметь источник и время доступности; вычисление в train и inference совпадает; кандидат сравнивается с базой на том же горизонте и наборе допустимых точек.

## Шаг 5. Реализовать и выполнить обучение — после готовности шагов 1–4

План:

1. Добавить отдельный запускаемый процесс обучения, конфигурацию эксперимента, фиксируемый seed и журнал версий.
2. Обучить простую регуляризованную регрессию на подготовленных признаках; оценить её против базы.
3. Только затем сравнить более сложный табличный кандидат; внешние признаки подключать по одному, измеряя их вклад.

Выбор конкретной библиотеки и её совместимой версии выполняется при реализации этого шага. Добавить зависимости согласованно в **существующие** `requirements.txt` и `pyproject.toml`; второй requirements не нужен. Установка текущего проекта сама по себе не устанавливает будущий обучающий стек.

### Предлагаемые новые файлы — сейчас их нет

| Будущий путь | Ответственность |
|---|---|
| `ml/training/prepare.py` | Собрать обучающие примеры по выбранной постановке из проверенных данных; не скачивать источники и не переписывать оригиналы. |
| `ml/training/train.py` | Прочитать конфигурацию, обучить преобразования и модель только на train, сохранить кандидат. |
| `ml/training/evaluate.py` | Пройти временные folds, отдельно получить candidate и baseline, сохранить прогнозы и метрики. |
| `ml/training/export.py` | Проверить полноту артефактов и записать неизменяемую версию модели с паспортом. |
| `ml/experiments/<имя>.json` | Настройки задачи, ревизии данных, даты, признаки, seed и параметры; без секретов. |

Это отдельный внешний слой. Обучающая библиотека не должна попасть в `tram/domain` или `tram/application`. Текущий `ml/src/tram_ml` также ограничен stdlib/domain архитектурным тестом. Новые внешние модули должны получить явные правила зависимостей и проверки; обходить тест размещением импортов в непроверяемой подпапке нельзя. Конкретный публичный CLI обучения добавить вместе с реализацией и тестами. **Пример несуществующей команды `python ... train` здесь намеренно не выдаётся за инструкцию запуска.**

**Результат:** версия кандидата в [models](../models/README.md), воспроизводимая конфигурация, прогнозы проверки. **Ревью:** повторяемость, отсутствие обучения при импорте/API-запросе, согласованность признаков, безопасная обработка неизвестных категорий и пропусков.

## Шаг 6. Проверить качество и принять решение

План:

1. Сравнить candidate и baseline на одинаковых точках финального test.
2. Проверить общую ошибку, часы пик, отдельные маршруты и покрытие прогнозов.
3. Проверить ограничения значений, скорость и устойчивость к отсутствующему контексту.

Сохранять **MAE** в единицах целевого ряда и **WAPE** с явной формулой `sum(abs(y - prediction)) / sum(abs(y))`; при нулевом знаменателе WAPE не определён. Указывать долю покрытия, число пропусков и исключений: нельзя улучшить метрику, молча исключив сложные точки. Для квартального метро вместо почасовых пиков использовать подходящие срезы станций/периодов.

Порог допуска и допустимое ухудшение на важных срезах зафиксировать до финального теста, с учётом назначения результата. Одного выигрыша на одном fold недостаточно для заявления об общей точности. Негативные прогнозы количества пассажиров недопустимы; если применяется ограничение снизу, оно одинаково работает в оценке и production. Доля заполнения может быть выше 1 при перегрузке — нельзя автоматически обрезать её до 100%.

Если нужны интервалы неопределённости, калибровать их на отдельном временном участке внутри development-данных и проверять покрытие на test. Сценарии короткой/длинной поездки сами по себе не являются статистическим доверительным интервалом.

**Результат:** паспорт модели и решение «допустить / оставить базу». **Ревью:** никаких метрик обучения вместо тестовых; ограничения качества и происхождения меток явно перечислены. Обученный кандидат может быть отклонён.

## Шаг 7. Подключить принятую модель через архитектуру проекта

Одного файла весов или записи в manifest сейчас недостаточно. План изменений:

| Существующая граница/файл | Необходимое расширение |
|---|---|
| `application/ports.py`, `Predictor` | Сохранить внедрение через порт. Для внешних признаков спроектировать явный документ/порт контекста, не выполнять HTTP внутри модели. |
| Новый адаптер в `infrastructure` | Проверять версию, SHA-256, схему признаков и зависимости; загружать доверенный артефакт, выполнять только inference. |
| `composition.py` | Собрать адаптер, хранилище версий и стратегию выбора. |
| `application/publication.py`, `service.py`, `worker.py` | Сейчас допускают только `seasonal_naive_v1`. Добавить регистрацию и проверку поддерживаемого метода, совместимости профиля и времени доступности модели. |
| `application/evaluation.py` | Отдельно считать кандидат и базу; текущую дублирующую baseline-оценку нельзя представить сравнением обученных моделей. |
| `openapi.yaml` и HTTP-слой | Проверить, что схема модели/отчёта выражает новый метод и происхождение; расширять контракт вместе с обработчиками при необходимости. |
| `tests/` | Предсказания до/после сохранения, несовместимая схема, отсутствующий/повреждённый артефакт, временная доступность, API → worker → результат. |
| `frontend/` | Проверить выбор метода, версию модели, качество и объяснимые ошибки; вычисления и обучение остаются вне UI. |

Для модели, обученной сегодня, production `available_at` не ставить задним числом ради старых folds. Backtesting — отдельный воспроизводимый эксперимент с обучением на разрешённом прошлом каждого fold; сохранить границы обучения и дату фактического запуска. При отсутствии/несовместимости артефакта вернуть явную ошибку либо объявленную политику fallback, не подменять метод в ответе незаметно.

**Результат:** прогноз принятой моделью через существующий API с известной версией данных/модели; обучающий процесс остаётся отдельным. **Ревью:** чистые зависимости сохранены, контракт/тесты и документация обновлены, пользователь видит фактический метод расчёта.
