# ADR 0003: роли при регистрации и сосуществование со статическими токенами

Статус: принято, реализовано. Основание — раздел «Расширение backend HTTP API» в [IMPLEMENTATION_PLAN.md](../../IMPLEMENTATION_PLAN.md#4-apiv1auth-логин-refresh-logout) (`AUTH1`–`AUTH4`), доведено до кода в PR #3 «secure user and operator registration» (`feature/t01-auth-registration`) и PR #4 «limit failed login attempts» (`feature/t02-login-rate-limit`).

## Контекст

До этого решения единственным механизмом авторизации был статический Bearer-токен из `.env` (`TRAM_VIEWER_TOKEN`/`TRAM_OPERATOR_TOKEN`, `hmac.compare_digest`) без пользователей и логина — осознанный выбор P0 для закрытого стенда (`openapi.yaml`: «Выдача токенов, регистрация и пароли не входят в P0»). Нужен был реальный логин с ролями `viewer`/`operator`, но публичная регистрация не должна тихо выдавать `operator`: `operator` может запускать прогнозы (`POST /forecast-runs` и другие защищённые POST), и самостоятельная выдача этой роли любому анонимному посетителю была бы повышением привилегий без проверки.

## Решение

1. **`POST /auth/register`** — публичная (`security: []`), всегда создаёт пользователя с ролью `viewer`. Тело запроса не принимает поле `role` вовсе (`UserCredentials` в контракте не содержит `role`; переданное лишнее поле — `422`, проверено `test_public_registration_does_not_accept_role`). Роль назначает сервер (`AuthService.register` жёстко зовёт `_create_user(..., "viewer")`), а не клиент.
2. **`POST /auth/operators`** — создание учётной записи `operator` требует уже действующего Bearer-токена с ролью `operator` (`security: [bearerAuth]`, `403` для `viewer`, `401` без токена). Token может быть как JWT от логина существующего оператора, так и статический `TRAM_OPERATOR_TOKEN`.
3. **Bootstrap первого оператора.** Пока в `users` нет ни одного `operator`, единственный путь создать его — статический `TRAM_OPERATOR_TOKEN` из `.env` при включённом `allow_static_tokens` (по умолчанию `true`). После этого первый оператор логинится по паролю и создаёт следующих через `/auth/operators`, статический токен становится не обязателен для повседневной работы.
4. **Статические токены не отключаются автоматически.** `authorize()` в `api/app.py` сначала сравнивает Bearer-токен со статическими `viewer_token`/`operator_token`, и только если оба сравнения не совпали — проверяет его как JWT через `auth_service`. Оба пути дают одинаковую роль остальному коду. Отключение статических токенов в проде (`allow_static_tokens=false`) — отдельное, не автоматическое решение эксплуатации; до него `tests/browser_server.py` и ручной сценарий `docs/TESTING.md` продолjают работать без изменений.
5. **Логин защищён от подбора пароля.** Пять неудачных попыток на пару «логин + IP» за 15 минут → `429 RATE_LIMITED` с `Retry-After` (см. PR #4); счётчик хранится в БД (`backend/migrations/versions/0005_login_attempts.py`) и общий для всех процессов API, не только для одного воркера.

## Альтернативы и почему отклонены

- **Разрешить `role` в теле `/auth/register`.** Отклонено: любой аноним получал бы `operator` по желанию — противоречит уже принятой модели «operator запускает расчёты» из основного контракта.
- **Один общий провижининг-скрипт/CLI вместо HTTP-эндпоинта `/auth/operators`.** Рассматривалось в исходном плане (`docs/IMPLEMENTATION_LOG.md`, открытый вопрос §6 в IMPLEMENTATION_PLAN.md), но `/auth/operators` с проверкой роли через тот же Bearer-механизм проще для команды из нескольких операторов и не требует доступа к серверу/БД напрямую.
- **Убрать роли совсем (единый плоский доступ).** Обсуждалось отдельно 27.09.2026 и сознательно отклонено: роли остаются, эта ADR фиксирует именно двухролевую модель, а не её отмену.

## Последствия

Приватный `password_hash` и служебные поля не покидают `application`/`infrastructure`: `/auth/me` и ответы `login`/`refresh` отдают только `id`/`username`/`role` (`tests/test_api.py::test_jwt_authorization_flow` проверяет отсутствие `password_hash` в ответе). Дальнейшее расширение ролей (например, отдельная роль только для чтения моделей) потребует новой ADR, а не молчаливого добавления значения в `CheckConstraint`.
