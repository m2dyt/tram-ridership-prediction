# Оценка наполненности с сохранением остатка пассажиров

Статус: реализованы три сценария, состояние рейсов, журнал, API, replay, временная агрегация и интерфейс. Модели не обучались; допущение о выходах требует независимой проверки.

## Текущая реализация

Реализованы domain-баланс, SQL-состояние и checkpoints, API, replay, экспорт средних по времени, интерфейс и сценарный калькулятор. Подробные команды: [OPERATIONS.md](OPERATIONS.md). Ниже — модель и исходные критерии; проверка точности на независимых реальных выходах ещё не выполнена.

## 1. Что оцениваем

Для каждого вагона и рейса ведём число оставшихся пассажиров после остановки. Люди, севшие на одной остановке, образуют группу (когорту). Это агрегированная масса пассажиров, а не идентификация конкретных людей.

На остановке `i` сначала выходят пассажиры из прежних групп, затем добавляются новые посадки:

```text
остаток_после_i = остаток_до_i − оценённые_высадки_i + посадки_i
0 ≤ оценённые_высадки_i ≤ остаток_до_i
```

Пример: до остановки 30 пассажиров, оценка высадок 8, посадки 12 → после остановки 34. На следующую остановку переносится 34, а не только последние 12. Дробный остаток допустим как математическое ожидание; округлять только отображение, не внутреннее состояние.

По одному минимальному и максимальному времени невозможно восстановить реальные назначения поездок. Можно построить сценарии высадок и проверить их позднее по наблюдениям. Поэтому результат первой версии — `estimated`, а не `observed`.

## 2. Какие входы обязательны

| Вход | Зачем нужен | Если отсутствует |
| --- | --- | --- |
| ID вагона, рейса, служебная дата, направление и версия сети | Не смешивать пассажиров разных вагонов/рейсов | Расчёт конкретного вагона недоступен; маршрутные суммы не делить поровну между вагонами |
| Порядок остановок и фактические/прогнозные времена их посещения | Разрешать высадки только на достигнутой остановке | Оценка времени по расписанию маркируется отдельно; геометрия сама по себе не даёт времени движения |
| Посадки по остановке и вагону | Добавлять новые группы | Валидации можно использовать только через явную модель оценки посадок с ограничениями |
| Начальный остаток и основание его значения | Запустить баланс | Нельзя молча считать вагон пустым в середине рейса; `unknown_initial_load` |
| Вместимость конкретного вагона/состава | Рассчитать долю заполнения | Число людей возможно, `occupancy_ratio` недоступен |
| Время доступности каждого входа | Отсечь будущую информацию | Неподтверждённые сведения не включаются в расчёт на `as_of` |

Валидации, посадки и уникальные люди — разные показатели. Если связь оплат и посадок не подтверждена, основной опубликованный показатель остаётся `validations`; модель наполненности доступна только как явно обозначенный эксперимент/сценарий.

## 3. Минимальное и максимальное время

Для группы, севшей на остановке `k`, строим времена до следующих допустимых мест высадки `τ₁ … τₙ` по оставшейся части рейса:

Времена должны быть положительными и строго возрастать. Ошибки порядка, одинаковые времена из грубого округления и отсутствующие посещения требуют проверки входных данных; деление на нулевую длительность недопустимо.

- `T_min = τ₁`: до следующей остановки, где разрешена высадка.
- `T_max = τₙ`: до конечной с обязательной высадкой, если такая граница подтверждена правилами рейса.
- Время берётся из телеметрии для уже пройденного участка либо из расписания/модели движения, доступной на `as_of`, для будущего.

Три первых сценария:

| Сценарий | Правило | Смысл |
| --- | --- | --- |
| Короткая поездка | Вся группа выходит на следующей допустимой остановке | Нижняя сценарная граница остатка при заданных посадках и начальном состоянии |
| Длинная поездка | Вся группа остаётся до подтверждённой конечной | Верхняя сценарная граница на тех же входах |
| Центральная эвристика | Вероятности высадки на следующих остановках из распределения длительности | Рабочая гипотеза, требующая проверки, а не оценка точности |

Границы сценариев не являются 95%-м доверительным/предиктивным интервалом и не заполняют `prediction_interval` действующего API.

### Первая центральная эвристика без обучения

Как явное проектное предположение используем равномерное распределение желаемой длительности на `[T_min, T_max]`. Его нельзя принимать за реальное распределение пассажиров. На следующем этапе оно заменяется проверенными распределениями по времени суток, типу остановки и направлению.

Высадку привязываем к ближайшему допустимому времени посещения остановки. Границы ячеек — середины между соседними `τ`; крайние границы — `T_min` и `T_max`. Если `F` — функция распределения длительности, вероятность высадки на остановке `j` равна `p_j = F(b_j) − F(b_{j−1})`. Сумма вероятностей равна 1. Если осталась одна остановка (`T_min=T_max`), ей назначается вся масса.

Например, следующие остановки через 5, 15 и 25 минут: границы ячеек 5, 10, 20, 25; вероятности 0.25, 0.50, 0.25. Для группы из 20 ожидаются высадки 5, 10, 5; её остаток после этих остановок — 15, 5, 0. Это пример арифметики гипотезы, не пассажирские данные Москвы.

Нельзя списывать пассажиров посреди участка только потому, что прошло несколько минут. При задержке вагона меняются ожидаемые времена; уже сохранённые высадки не повторяются. Для перерасчёта будущих вероятностей нормируется только оставшаяся масса по ещё достижимым остановкам.

## 4. Группы и остаток

Для группы `k` храним первоначальные посадки `B_k`, вероятности по будущим остановкам `p_kj`, накопленные высадки и остаток `R_k`. На остановке `j`:

```text
высадки_группы_kj = B_k × p_kj
R_k(после j) = B_k − сумма высадок группы до j включительно
наполненность_после_j = сумма R_k(после j) по прежним группам + новые посадки_j
```

Это безусловные вероятности относительно исходного `B_k`. Если применять вероятность к текущему остатку, сначала нужна условная нормировка; иначе получится другой баланс. Каждая новая посадка добавляется отдельной группой после высадок.

Метро, хабы, погода и мероприятия могут позднее менять вероятности назначения и прогноз посадок. Коэффициенты такого влияния нельзя объявлять установленными без проверки. Первые эксперименты сравнивают сценарии на одинаковых данных.

Конечная обнуляет остаток только при подтверждённом завершении пассажирского рейса с обязательной высадкой. Для кольцевых маршрутов, сквозных рейсов и смены направления без высадки требуется отдельная политика переноса групп и максимальной длительности/числа кругов. Одинаковый `stop_id` на кольце различается позицией и посещением.

## 5. Постоянное состояние и восстановление

Планируемые сущности, пока без миграции:

| Сущность | Содержимое |
| --- | --- |
| `vehicle_trip_state` | Вагон/состав, рейс, служебная дата, маршрут/направление, версия сети, последнее обработанное посещение остановки, остаток, качество, версия состояния |
| `passenger_cohorts` | ID группы, остановка/посещение посадки, время посадки, исходная и оставшаяся масса, версия метода, будущие вероятности высадки |
| `stop_visit_events` | Уникальный ID события, время события и получения, последовательность, входные посадки/наблюдаемые высадки, ссылки на исходные записи |
| `occupancy_checkpoints` | Снимок групп и остатка, позиция входного потока, версии данных/алгоритма; основа воспроизведения |

Остаток, группы, выходные значения и отметка обработанного события сохраняются одной транзакцией. Повтор события ничего не списывает. Конкурентные worker сериализуют обновление одного вагона/рейса блокировкой или проверкой версии; память процесса не является единственным хранилищем.

Поздняя правка приводит к воспроизведению от последнего подходящего checkpoint и новой версии результата. Исторические прогнозы не переписываются задним числом. При пропавшей телеметрии состояние становится неполным/устаревшим; таймаут сам по себе не означает, что люди вышли. Начальное неизвестное состояние разрешается измерением или подтверждённой точкой очистки вагона.

## 6. Связь с существующим API и архитектурой

`domain` содержит баланс и инварианты; `tram_ml` — стратегию вероятностей без I/O; `application` — обработку посещения, replay и порт состояния; `infrastructure` — SQL, телеметрию и источники. Внешние HTTP-запросы не выполняются внутри расчёта групп или GET API.

Наполненность на участке берётся после отправления с предыдущей остановки. Для текущего агрегированного API сохраняется средняя наполненность **одного вагона**, взвешенная по длительности наблюдаемых проездов в интервале. Для доли заполнения сначала делится остаток каждого вагона на его вместимость, затем выполняется временное взвешивание. Сумма по вагонам — иной показатель и не выдаётся под тем же профилем.

Результат реконструкции публикуется как `ObservationPoint.value_kind=estimated`, с `estimation_method=cohort_duration_uniform_v1`, флагами допущений и версией входов. До проверки точности качество `unverified`. Прогноз такого ряда имеет `value_kind=forecast`; происхождение исходной оценки сохраняется в профиле/манифесте. `source_mode` описывает происхождение потока и не заменяет `value_kind`.

Переполнение не скрывается обрезанием до вместимости: `occupancy_ratio > 1` сохраняется с флагом для проверки оценки/источника. Превышение численной погрешности в отрицательном остатке или нарушение баланса считается ошибкой, а не исправляется без следа через `max(0, ...)`.

В OpenAPI реализованы `/occupancy-trips`, состояние отдельного рейса и журнал событий; список рейсов поддерживает `vehicle_id`. Команда `export-occupancy` строит агрегаты участков из журналов и сохраняет prepared bundle. Исторические профили публикуются после проверки; доступные прогнозы не объявляются автоматически без достаточной истории.

## 7. План реализации и критерии ревью

1. Аудит: получить посадки, посещения остановок, идентификаторы рейсов/вагонов, начальное состояние и вместимость; явно отметить отсутствующие входы.
2. Domain/ML: три сценария, баланс групп, одна оставшаяся остановка, отсутствие высадки посреди участка; без обучения.
3. Application/SQL: постоянное состояние, транзакционная обработка события, повтор, restart, конкуренция, replay поздних исправлений.
4. Агрегация: участки и временные интервалы, раздельные вместимости вагонов, существующий формат `estimated`.
5. Проверка на независимых наблюдениях: ошибка наполненности и высадок, покрытие, чувствительность к распределению длительности, отдельные результаты для хабов и обычных остановок.

Обязательные проверки: сохранение массы, 30−8+12=34, перенос группы через несколько остановок, запрет двойного списания, восстановление после перезапуска, раздельность вагонов, кольцо, задержка, неизвестное начальное состояние, неизвестная вместимость, переполнение и отсутствие будущих данных на `as_of`. В каждой реализации — план перед шагом и ревью сразу после него.
