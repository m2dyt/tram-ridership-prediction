## 1. Цель и правила хакатона

Целевой показатель для конкурса — **общий пассажиропоток по маршруту и часу**, в сетке ноябрь–декабрь 2025. Не выдавать его за число людей в вагоне или за поток по конкретной остановке: организаторы подтвердили, что `bus_stop_no` не даёт требуемого соответствия и остановочная детализация факультативна. `place_id` и `bus_exit_no` не использовать без однозначного словаря.

Показатель качества из спецификации: `WAPE-score = max(0, 1 - sum(abs(y - prediction)) / sum(y))`; ориентир высшей категории — выше 0.88. Нулевой знаменатель обрабатывается явно. Организаторы сообщили, что ошибочный маршрут 5 всё равно должен быть в файле и его можно заполнить нулями либо виртуальными прогнозами. Лидерборд, по ответам организаторов, учитывает весь ноябрь–декабрь и лучший загруженный результат; перед отправкой сверить актуальный дедлайн и лимиты на платформе. По PDF текущий дедлайн — 27.09.2026, 23:59 МСК.

Внешние данные разрешены, в том числе опубликованные после 31.10.2025. Для честного вывода разделять две постановки:

- **соревнование/ретроспектива:** разрешённые фактические архивные погодные сведения допустимы, если правила площадки не изменились;
- **прогноз вперёд/работа API:** признак должен быть известен в `as_of`. Для погоды использовать исторический выпуск прогноза (`issued_at`) с подходящим горизонтом, а не фактическое наблюдение будущего.

Источником критериев служат приложенная спецификация хакатона (`C:\Users\USER\Downloads\ИИ-прогноз загрузки трамвайных маршрутов.pdf`) и ответы организаторов, переданные владельцем проекта.

## 4. Пошаговая реализация

У каждого этапа конкретный кодовый результат. Проверки перечислены в конце как review/acceptance, а не как самостоятельный результат этапа.

### Этап 0 — зафиксировать конкурсный результат

**Реализовать/подготовить:** сохранить лучший принятый сабмит независимо от текущего файла; зафиксировать receipt/score, имя, дату, SHA-256 и версию кода; сделать генерацию нового CSV в отдельный каталог-кандидат; реализовать сравнение submission с sample по ключам/порядку/типам; всегда выводить маршрут 5.

**Review:** точные уникальные ключи, никаких пропусков/NaN/inf/отрицательных значений, разделитель и колонки совпадают с площадкой, лучший вариант не перезаписан. Не отправлять новый вариант без отдельного решения владельца.

### Этап 1 — сделать входные данные воспроизводимыми

**Новые deliverables:**

- `scripts/prepare_tram_challenge.py` — CLI распаковки/импорта, без изменения исходного архива;
- `ml/training/tram_data.py` — проверка схемы, типов, ключей, нулей/NA, покрытия и соответствия sample/test;
- `data/training/tram-competition-v1/manifest.json`, нормализованные train/validation/test/sample и машинный отчёт качества;
- provenance в `sources/` с хешами, URL, временем получения и версией словаря.

**Review:** ноль отличим от отсутствующей строки; необъяснённый дубль или несовместимая схема останавливают pipeline с понятной ошибкой; тестовая целевая переменная не загружается в train.

### Этап 2 — разложить и сделать проверяемым текущий трамвайный тренер

**Новые deliverables:** модули `ml/training/tram/features.py`, `baseline.py`, `models.py`, `evaluation.py`, `submission.py`, `cli.py`; текущий `train_tram.py` оставить совместимой CLI-обёрткой на период миграции. Вынести генерацию сетки, календарные признаки, сезонные профили, лаги/остатки, обучение, метрики и формат CSV в отдельные функции.

Сначала реализовать сезонный baseline и точный WAPE-score. Затем добавить как минимум Ridge и HistGradientBoosting кандидатов. Сохранить конфиг с датами folds, перечнем признаков, seed и параметрами. Сделать rolling-origin оценки, сохранить прогнозы каждого fold, общие метрики и срезы по маршруту/часу/месяцу/типу дня. Существующие route-specific поправки проверять по одной; убрать те, которые не дают устойчивого выигрыша на validation.

**Review:** train и validation временны́е, preprocessing обучается только на train fold, никакие фактические значения target после cutoff не попадают в лаги, сравнения сделаны на одинаковом coverage. Финальный test не используется для подбора.

### Этап 3 — построить настоящие внешние feature pipelines

**Новые deliverables:** погодный fetch/cache/normalizer; `calendar.py` для официального календаря; подготовленные `weather.parquet` и `calendar.csv`; join по времени, единицам и версии маршрута; конфигурация, позволяющая выключать каждый источник. Для weather хранить источник/model/`issued_at`/`valid_at`/lead; для календаря — источник нормы и версию таблицы.

Сделать отдельную матрицу сравнений: baseline → +calendar → +weather → +оба. После этого, если исторический источник будет доступен, добавить traffic/events importers с тем же контрактом provenance и отдельной абляцией. Если источника или лицензии нет, оставить явный `not_available`, не заполнять произвольным нулём и не блокировать работу основной модели.

**Review:** timezone Europe/Moscow соблюдён, покрытие и unmatched видны, train/live использует корректную доступность данных, прирост оценивается по WAPE-score на тех же строках.

### Этап 4 — сделать выпуск модели воспроизводимым

**Новые deliverables:** CLI `tram model train`, `tram model evaluate`, `tram model export`; конфигурации `ml/experiments/tram_*.json`; уникальный `models/tram/<version>/` bundle с estimator, feature schema, config, splits, метриками, зависимостями, SHA-256 исходников/кода и model card. Добавить валидатор manifest/checksum и запрет перезаписи уже выпущенной версии. Отдельно сделать `best`/`candidate` alias, переключаемый только явной командой.

**Review:** после сериализации модель выдаёт тот же результат; loader читает только совместимую доверенную версию; train/validation/test имеют подтверждённое происхождение; обучение не запускается при импорте Python пакета или старте API.

### Этап 5 — подключить estimator к существующему backend

**Новые deliverables:** `ArtifactPredictor` в infrastructure/ML adapter, выбор model version через settings/composition root, fallback на `SeasonalNaive`, batch/live feature service, поля model ID/version и `as_of` в метаданных результата при согласовании OpenAPI. Сохранить разделение domain/application и библиотек обучения; fit и скачивание данных не выполнять в запросе API.

Если существующий `Predictor` контракт не может выразить нужный контекст или горизонт, расширить его порт и DTO минимально необходимыми полями и согласованно поменять worker/API/OpenAPI/хранилище с миграцией только при реальной необходимости.

**Review:** интеграционный сценарий API → worker → `ArtifactPredictor` выдаёт прогноз выбранной версии; отсутствие/несовместимость bundle приводит к явной ошибке readiness или включаемому fallback; прогноз и метаданные содержат версию и время отсечки.

### Этап 6 — эксплуатация, зависимости, запуск и документация

**Новые deliverables:** один корневой `requirements.txt` для стандартной установки; опциональные training extras в `pyproject.toml`; команды CLI для подготовки, обучения, оценки и экспорта в документации; примеры вызова API/Swagger; benchmark скрипт или сценарий, сохраняющий p50/p95/p99, RPS, процент ошибок, CPU/RAM и конфигурацию. Папочные README описывают ответственность своих файлов. Текущие требования PDF к p95/RPS — цель, не обещание до замера.

**Review:** чистая установка на Python 3.12; обучение и API запускаются раздельно; backend benchmark повторяем; ссылки локальной документации работают; root README ведёт сюда.

### Этап 7 — отделить квартальный эксперимент метро

**Новые deliverables:** исправить `line_name`/`line` mapping в `ml/training/prepare.py`; привести GBDT категориальные данные к контракту установленного sklearn; запретить случайное перезаписывание metro artifact; записывать версии/хеши. Документировать metro как отдельный quarterly experiment, а не часть трамвайного competition score.

**Review:** две задачи не смешивают target, частоту, splits, dataset и score; примеры и инструкции воспроизводятся на локальных metro данных.

## 6. Архитектура итогового решения

```text
sources/ originals + licenses + hashes
    → scripts/ import / audit
    → data/ normalized labels + weather + calendar + feature tables
    → ml/training/ baselines + candidate fits + temporal evaluation
    → models/tram/<version>/ immutable bundle + manifest + model card
    → backend infrastructure ArtifactPredictor
    → application Predictor port → worker → PostgreSQL results
    → FastAPI/OpenAPI: forecast + model metadata + health/readiness
```

`ml/src/tram_ml` остаётся чистым слоем общих типов/простых функций. Pandas/sklearn/CatBoost при необходимости располагаются в `ml/training` либо infrastructure adapter, а не в `tram/domain`. API не обучает модели, не скачивает датасеты и не делает сетевые запросы к погоде синхронно на каждый прогноз.

## 7. Что будет считаться эталонным результатом

1. Конкурсный submission соответствует точному набору ключей и формату; все маршруты представлены, route 5 обработан по ответу организаторов.
2. Score воспроизводим на зафиксированной временной validation и подтверждён платформой; результат не объясняется утечкой или невидимым отбором строк.
3. Есть рабочие загрузчик и подготовка данных, честная политика `zero`/`missing`, provenance и полный CSV/JSON отчёт покрытия.
4. Модельный эксперимент содержит baseline и обучаемых кандидатов, временные folds, out-of-fold predictions, метрики/coverage по маршрутам и часам.
5. Погода и календарь имеют реально реализованные pipelines и показанный вклад; трафик/события включаются только при пригодной истории.
6. Версионированный model bundle повторно загружается и однозначно идентифицирует данные/код/зависимости/метрики.
7. Backend worker выдаёт прогноз через модельный adapter; fallback, model metadata, OpenAPI и benchmark задокументированы.
8. Один простой корневой план показывает, что делать дальше; README и папочные инструкции ведут к коду и запуску. Frontend не является критерием завершения этого плана.
