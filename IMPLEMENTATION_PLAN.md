## Дополнения пользователя от 21.09.2026

1. Использовать любые подходящие наборы [портала открытых данных Москвы](https://data.mos.ru/opendata): в том числе остановки, метро, пересадочные хабы и городской контекст. Для каждого выбранного набора фиксировать источник, версию, временное покрытие и качество. Конкретные ID подтверждать по доступным карточкам каталога.
2. Для оценки высадок учитывать минимальную поездку до следующей допустимой остановки и максимальную до подтверждённой конечной. Между ними задавать явную гипотезу длительности; результаты считать оценками, пока нет проверочных данных.
3. Сохранять группы посадки и остаток пассажиров по вагону/рейсу: `остаток = предыдущий остаток − высадки + посадки`. Состояние переживает перезапуск и не изменяется повторно при дублирующемся событии. Полная спецификация — [PASSENGER_OCCUPANCY.md](docs/PASSENGER_OCCUPANCY.md).
4. Frontend: **React на JavaScript/JSX + Vite, карта на OpenStreetMap**. Для первой реализации выбирается Leaflet. Прежнее предложение TypeScript заменено; детали — [ADR 0002](docs/decisions/0002-frontend-stack.md).
5. Добавить погодные и событийные источники: первым погодным адаптером планируется Open-Meteo, альтернативным — WeatherAPI.com; для мероприятий — KudaGo и Timepad после проверки доступа. Документация, примеры запросов и фактические результаты сетевых проверок — в [DATA_SOURCES.md](docs/DATA_SOURCES.md).

Эти дополнения зафиксированы как требования и план следующих реализаций. Сейчас не добавлены автоматические загрузчики, постоянное состояние групп пассажиров и frontend. Рабочий backend, сезонная база и действующий OpenAPI сохраняют ранее описанную готовность; обучение по-прежнему не запускается.

### 2. Данные для рендера карты: пробелы и решения

Карта (`Map.jsx`) сегодня рисует три слоя: сеть маршрута (`route.directions[].geometry`, `route.stops[].geometry` — из `RouteDetail`), результат прогноза (`forecast.features` — из `/forecast-runs/{id}/map`, GeoJSON `Point`/`LineString`/`MultiLineString` по `SpatialLevel`) и контекст (`context` — плоский `{coordinates,title,category}` из `GeoRecord`, не GeoJSON, координаты собираются вручную). Точки остановок и маршруты из запроса пользователя это уже покрывает; реальных пробелов три.

#### 2.1 Целая сеть одним вызовом

`GET /routes` не содержит геометрию (её даёт только `GET /routes/{route_id}`), поэтому карта «вся сеть» сейчас требует N запросов на N маршрутов. Предлагается новая операция `GET /network` — `{network_revision_id, valid_at, items: RouteDetail[], page}` (по структуре как `RoutePage`/`StopPage`, но с полным `RouteDetail` в `items`), а не условный `expand`-параметр на `/routes`: в этом контракте одна операция даёт одну схему ответа, менять её по значению query-параметра означало бы отступить от уже принятого стиля (`additionalProperties:false`, фиксированная схема на каждый `operationId`).

#### 2.2 Несколько маршрутов в одном запросе

Пространственные фильтры (`route_id` и то, что от него зависит — `direction_id`/`stop_id`/`segment_id`) сейчас принимают одно значение. Важно: текущий разбор параметров в `app.py::parameters()` явно отклоняет повтор одного query-параметра («Parameter must occur once»), поэтому **простой repeated `route_id=a&route_id=b` работать не будет без изменения этой общей проверки**. Предлагается вариант без этого изменения: `route_id` через запятую в одном параметре (`route_id=demo-route-01,demo-route-02`, `schema: {type: array, items: {...}, style: form, explode: false}`), с лимитом 100 — по аналогии с `max_routes_per_run` в `Capabilities`. Разбор — в тех же местах, где сейчас читается одиночный `route_id` (`ReadService.validate_spatial`, `repository.observation_points/forecast_points/evaluation_points`).

#### 2.3 Контекстные слои как GeoJSON

`GeoRecord` (`{id,title,coordinates,category}`) — не `Feature`, поэтому `Map.jsx` вручную реверсит координаты вместо переиспользования `L.geoJSON(...)`, которым уже рисуется прогноз. Новая операция `GET /context/snapshots/{snapshot_id}/geojson` (`application/geo+json`, `FeatureCollection` с `Feature.geometry=Point`, `properties={id,title,category}`) — отдельная операция по тому же принципу, что и `/forecast-runs/{run_id}/map` относительно `/forecast-runs/{run_id}/points`, а не смена media type по query-параметру.

### 3. Уведомление на карте о загрузке маршрута

Формулировка задачи допускает два разных смысла — оба стоит спроектировать, но с разным статусом готовности.

#### 3.1 Трек А — расчёт прогноза выполняется/готов (P0/P1, готово к реализации)

Сегодня `Forecast.jsx` поллит статус ОДНОГО уже выбранного/созданного запуска (`setTimeout` 2000 мс, пока `status in (queued,running)`); на карте до выбора маршрута и запуска никакого индикатора нет. Предложение — без новой инфраструктуры, тем же поллингом:

1. `GET /forecast-runs` получает новый необязательный параметр `active` (`true` ⇒ эквивалент `status in (queued,running)` без второго вызова с `status=queued` и ещё одного с `status=running`); вместе с `route_id` из §2.2 один запрос покрывает все видимые на карте маршруты.
2. `ForecastRunPage` получает поле `recommended_poll_seconds` (по аналогии с `DataStatus.recommended_poll_seconds`) — контрактное изменение (`additionalProperties:false`, нужно добавить в `required`/`properties`).
3. Поведение карты: пока для маршрута есть активный `run`, `Map.jsx` показывает бейдж «прогноз загрузки маршрута рассчитывается» на слое маршрута; при переходе в `succeeded` — одноразовое уведомление «прогноз готов» (пользователь сам решает переключить карту на этот `run_id`, без автоматической подмены — так же, как уже описано поведение при смене `dataset_revision_id` в `openapi.yaml`); при `failed` — предупреждение с `failure.message`, без деталей исключения.

#### 3.2 Реализация трека А

Изменения только в уже существующих операциях: `service.py::ReadService.runs` (фильтр `active`), `repository.py` (SQL-условие по статусу), `openapi.yaml` (`parameters.RunStatus`-подобный новый параметр + поле в `ForecastRunPage`). Новых таблиц/фоновых процессов не требуется.

#### 3.3 Трек Б — предупреждение о прогнозируемой повышенной загрузке (P1, не готово к реализации)

Это в точности нерешённый пункт `F10` исходного плана (раздел 10 ниже): нужен согласованный показатель, порог, период и правило снятия предупреждения, и «спрос не должен называться перегрузом вагона» без проверки. Ничего из этого не появилось с момента первой формулировки, поэтому здесь не фиксируется число. Проектное place-holder — отдельная операция `GET /forecast-runs/{run_id}/alerts`, а не поле в самом `ForecastPoint`: чтобы не смешивать проверенный контракт прогноза с эвристикой сравнения, которая ещё не согласована. Реализация блокирована пунктом «порог» в таблице §6.

### 4. `/api/v1/auth`: логин, refresh, logout и регистрация

Статические Bearer-токены из `.env` (`TRAM_VIEWER_TOKEN`/`TRAM_OPERATOR_TOKEN`, сравнение через `hmac.compare_digest`) продолжают работать для закрытого стенда и тестов. Параллельно пользователи входят по логину/паролю; API выдаёт JWT и refresh-cookie. Публичная регистрация назначает только `viewer`; создание пользователя с ролью `operator` доступно лишь действующему оператору. Это сохраняет сценарии `docs/TESTING.md` и `tests/browser_server.py` со статическими ключами.

#### 4.1 Эндпоинты

| Операция | Тело/вход | Ответ 200 | Ошибки |
| --- | --- | --- | --- |
| `POST /auth/register` (`security: []`, публичная) | `{"username","password"}`; роль `viewer` задаёт сервер | `{"id"}` | `400` неверное тело, `422` поля не прошли контракт или имя уже занято |
| `POST /auth/operators` (Bearer, роль operator) | `{"username","password"}`; роль задаёт сервер | `{"id"}` с новой учётной записью operator | `400` неверное тело, `401` нет/неверный токен, `403` роль viewer, `422` поля не прошли контракт или имя уже занято |
| `POST /auth/login` (`security: []`, публичная) | `{"username","password"}` | `{"access_token","token_type":"bearer","expires_in","role","user":{"id","username"}}`; refresh — `Set-Cookie: tram_refresh=…; HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth` | `400` неверное тело, `401 UNAUTHORIZED` неверные логин/пароль (без уточнения, какое поле неверно), `429 RATE_LIMITED` при повторных неудачных попытках |

Для `/auth/login` лимит составляет пять неудачных попыток на пару «логин + IP» за 15 минут от первой попытки. Следующий запрос получает `429` и `Retry-After` в секундах; успешный вход сбрасывает счётчик. Неизвестные и отключённые пользователи проходят то же правило. Счётчики хранятся в БД и истекают через 15 минут.
| `POST /auth/refresh` (авторизация — cookie `tram_refresh`, не Bearer) | тело не требуется | новый `access_token` (как выше); refresh-cookie ротируется (старое значение отзывается) | `401 UNAUTHORIZED` — просрочен/отозван/отсутствует; фронт трактует как разлогин |
| `POST /auth/logout` (cookie `tram_refresh`) | необязательно `{"everywhere":bool}` | `204`, отзыв refresh-сессии (или всех сессий пользователя), `Set-Cookie` с `Max-Age=0` | безопасно вызывать без активной сессии |
| `GET /auth/me` (Bearer, viewer/operator) | — | `{"id","username","role"}` | `401` истёкший/невалидный access-токен |

Новых кодов в `Error.code` не требуется: используются уже существующие `UNAUTHORIZED`/`RATE_LIMITED`/`BAD_REQUEST`/`VALIDATION_ERROR` — намеренно без `INVALID_CREDENTIALS`/`TOKEN_EXPIRED`, чтобы не давать клиенту различать «неверный пароль» и «неверный логин» (тот же принцип, что уже в контракте: «Стек вызовов и идентификаторы пассажиров клиенту не выдаются»).

#### 4.2 Хранение и миграция

Новая ревизия `0004`: таблица `users` (`id` uuid pk, `username` unique, `password_hash`, `role` с тем же `CheckConstraint`, что у `RunRow.status`, `is_active`, `created_at`) и `refresh_tokens` (`id` pk, `user_id` fk, `token_hash` — хранится хэш, не сам токен, unique/indexed, `issued_at`, `expires_at`, `revoked_at` nullable, `replaced_by` nullable self-fk для цепочки ротации). Публичная регистрация создаёт `viewer`; operator создаёт отдельный защищённый endpoint. Первого оператора можно добавить настроенным статическим operator-токеном, если включён `allow_static_tokens`, затем доступен вход существующего оператора по JWT.

#### 4.3 Слои (по ADR 0001)

`domain/auth.py` (опционально) — чистая проверка формы логина/пароля, stdlib. `application/auth.py` — сценарии login/refresh/logout/me поверх новых портов `UserRepository`, `PasswordHasher`, `TokenIssuer`, `SessionStore` в `application/ports.py` (без импорта SQL/JWT-библиотек, как и остальной `application`). `infrastructure/auth.py` — SQL-репозиторий, argon2-хеширование пароля, выпуск/проверка JWT. `api/app.py::authorize` расширяется: сначала пробует статическое сравнение (как сейчас), затем — проверку подписи/срока JWT; оба пути дают роль для остального кода без изменений в обработчиках.

#### 4.4 Настройки и зависимости

`Settings` (`infrastructure/settings.py`): `auth_token_secret: SecretStr` (включить в `require_api_secrets()` — четвёртый секрет ≥32 символов, отличный от остальных), `access_token_ttl_seconds: int = 900`, `refresh_token_ttl_seconds: int = 30*86400`, `allow_static_tokens: bool = True` (пока не принято отдельное решение об отключении в проде — см. §6). Новые зависимости — в базовые `requirements.txt`/`pyproject.toml [project.dependencies]` (не в `optional-dependencies`, это не тренировочный экстра, а обязательный рантайм): `pyjwt>=2.9,<3`, `argon2-cffi>=23,<24`.

### 5. Реестр моделей: `GET /models`, `GET /models/{model_id}`

Строится поверх уже реализованного на `origin/etalon` формата (`models/tram/<version>/manifest.json|metrics.json|model-card.md`, `active_version.txt`, `ArtifactPredictor.from_active_version`) — см. «Основание» выше. `GET /models` (viewer+) перечисляет найденные версии: `{"items":[{"id","version","method","is_active","is_baseline","metrics":{...из metrics.json...}}], "page"}`; пагинация избыточна при ожидаемых единицах версий, но формат ответа держится совместимым с остальными списками. `GET /models/{model_id}` — тот же элемент плюс содержимое `config.json` и текст `model-card.md`.

Осознанно **не предлагается** `POST /models/{id}/activate` по HTTP: переключение активной версии уже задокументировано как явное действие эксплуатации (`Set-Content models/tram/active_version.txt …` в `docs/OPERATIONS.md` на `etalon`, `models/README.md`: «best/candidate alias, переключаемый только явной командой»). Инвертировать это в операцию, доступную любому `operator`-токену без отдельного review, значило бы отменить уже принятое архитектурное решение без нового основания.

## 2. Рабочие решения до получения ответов

Решения в этом разделе — проектные предположения, а не подтверждённые требования организаторов. У1 фиксирует их подтверждение или замену в журнале решений до завершения этапа 0.

### Показатели и пространственная детализация

| API-показатель | Единица | Условие доступности | Агрегация |
| --- | --- | --- | --- |
| `validations` | `validations` | Записи оплат | Сумма за интервал; не называется количеством людей |
| `boardings` | `passengers` | Измеренные посадки либо проверенная оценка | Сумма; оценка маркируется `estimated` |
| `occupancy` | `passengers` | Данные о пассажирах в вагоне или проверенная модель пассажирообмена | Для первой версии профиля — средняя наполненность одного вагона на участке, взвешенная по времени нахождения на участке |
| `occupancy_ratio` | `ratio` | Наполненность и вместимость соответствующих вагонов | Взвешенное по времени среднее отношений наполненности к вместимости; 1.0 = 100%, значения > 1 допустимы |

Уровни: `route`, `route_direction`, `stop`, `segment`. Остановка относится к маршруту и версии его последовательности; при известных направлениях — также к направлению. Повторный проход одной остановки в кольцевом маршруте различается `stop_sequence`. Показатели наполненности выдаются только на уровне участка. Среднее или долю нельзя суммировать по остановкам и времени. Валидации и посадки не являются числом уникальных пассажиров.

Внутри конвейера наполненность рассчитывается отдельно по вагону/рейсу с сохранением групп пассажиров. Текущий публичный контракт выдаёт агрегаты по участкам, а не индивидуальные вагоны. Для отдельного вагона потребуется расширение контракта вместе с реализацией. Минимальный/максимальный сценарии поездки не выдаются как статистический `prediction_interval`.

### Горизонты и время

| Горизонт | Предварительный шаг | Пример периода по Москве | Условие |
| --- | --- | --- | --- |
| `day` | `hour` | `[2026-09-21 00:00, 2026-09-22 00:00)` | Есть часовая история |
| `month` | `day` | `[2026-09-21 00:00, 2026-10-21 00:00)` | Есть суточная история |
| `year` | `month` | `[2026-10-01 00:00, 2027-10-01 00:00)` | Начало первого числа месяца; достаточно истории для проверки |

API передаёт RFC 3339 с явным смещением, например `2026-09-21T00:00:00+03:00`; хранение времени — UTC, календарные границы и интерфейс — `Europe/Moscow`. Все интервалы `[start, end)`. Для прибавления месяца/года отсутствующее число заменяется последним числом целевого месяца; например, месяц от 31 января заканчивается 28/29 февраля. Часовые интервалы по текущим московским правилам образуют 24 точки в сутках. Для `year/month` всегда 12 календарных месячных точек.

`as_of` — момент, на который доступны сведения для расчёта; `history_end` — исключающая верхняя граница использованной истории; `calculated_at` — реальное время завершения вычисления. Требуется `history_end <= as_of <= forecast_start`. Обучение, подбор гиперпараметров и внешние признаки также соблюдают границу `as_of`. Для истории публикаций нужен `available_at`, отдельно от времени события.

Доступность сочетаний задаёт `/capabilities`: клиент не предполагает, что каждый показатель, остановка или годовой прогноз доступны. Неподдерживаемый запрос получает 422 с объяснением. Пропущенное значение — `null` с причиной, а не 0. При отсутствии всего результата возвращается пустой список либо явный статус недоступности, в зависимости от операции.

## 3. Предлагаемая архитектура

```text
sources/ (только чтение)
    → аудит и карантин ошибок
    → Parquet: очищенные записи и признаки
    → агрегаты + версия маршрутной сети
    → обучение и backtesting (отдельные команды)
    → реестр проверенных моделей
    → worker: пакетный прогноз
    → PostgreSQL: неизменяемые результаты
    → REST API /api/v1
    → React: карта + статистика + единые фильтры
```

GET-запросы читают сохранённые результаты. POST задания прогноза запускает применение подготовленной модели; обучение через пользовательский HTTP-запрос не выполняется. Очередь первой версии — таблица заданий PostgreSQL с блокировкой при захвате, временем аренды и восстановлением после падения worker. Redis/Celery или другой брокер добавляется только при измеренной необходимости.

| Компонент | Предложение | Назначение |
| --- | --- | --- |
| API | Python + FastAPI + Pydantic | Проверка запросов и выдача готовых данных |
| Хранение | PostgreSQL + PostGIS | Справочники, геометрия, агрегаты, задания, результаты |
| Подготовка | Python, Polars или DuckDB, Parquet | Чтение миллионов записей порциями, группировка без загрузки всего набора в память |
| ML | Сезонный наивный метод, простая регрессия, затем кандидат на основе CatBoost | Сначала измеримое сравнение, затем выбор модели по backtesting |
| UI | React + JavaScript/JSX + Vite, OSM + Leaflet, библиотека графиков | Карта, графики и общие фильтры |
| Запуск | Docker Compose | API, worker, БД и frontend в воспроизводимом окружении |

Python/FastAPI для backend принят ранее, frontend уточнён пользователем 21.09.2026. Менять язык или платформу без нового требования не планируется. HTTP-загрузчики источников находятся во внешних адаптерах; ML и баланс пассажиров не зависят от сети, SQL или React.

Поставщик картографической подложки, лицензия, атрибуция и возможность работы на демонстрационном стенде уточняются до интеграции карты. Версии зависимостей фиксируются в lock-файлах при начале разработки.

## 5. Данные и хранение

| Сущность | Основные поля и правила |
| --- | --- |
| `dataset_revisions` | ID, manifest с хешами входов, период, время загрузки, версия конвейера, режим источника, отчёт качества; публикация версии атомарная |
| `network_revisions` | ID, период действия, маршруты, направления, порядок остановок, геометрия; изменения сети не затирают историю |
| `routes`, `route_directions`, `stops`, `route_stops`, `segments` | Внешние и внутренние ID, версия сети; `route_stops` содержит порядковый номер, а участок — две последовательные позиции |
| `observations` | Версия данных, ключ пространственной серии, показатель, `[start,end)`, значение, происхождение, покрытие, флаги качества |
| `feature_sets` | Версия данных, список признаков, `event_time`, `available_at`, правила расчёта; воспроизводимый снимок |
| `source_snapshots` (план) | Поставщик, ID/версия набора или выпуска, URL, время публикации/получения, хеш, условия использования; версии погоды и анонсов |
| `vehicle_trip_state`, `passenger_cohorts` (план) | Остаток по вагону/рейсу, группы посадки, метод распределения высадок, последнее событие и версия состояния |
| `stop_visit_events`, `occupancy_checkpoints` (план) | Уникальные посещения остановок и снимки для восстановления/пересчёта без двойного списания |
| `model_versions` | Артефакт, код/параметры, границы обучения, профили, версии признаков и результаты проверки |
| `forecast_runs` | UUID, профиль, область маршрутов, `as_of`, период, данные/сеть/модель, статус, попытки, heartbeat worker, ошибка |
| `forecast_points` | ID запуска, ключ серии, интервал, значение и необязательный диапазон, качество |
| `evaluation_reports` | Модель, горизонты, folds, даты отсечения, метрики модели и базовых методов, покрытие и ограничения |
| `evaluation_points` | Fold, ключ серии, интервал, факт, модель и базовые методы для исторического графика |

Уникальный ключ агрегата: версия данных + `series_key` + показатель + шаг + начало интервала. `series_key` однозначно кодирует маршрут/направление/позицию остановки или участок и никогда не равен SQL NULL. Это предотвращает дубли при nullable измерениях. API раскрывает отдельные поля этого ключа через `spatial`.

План индексов: `(dataset_revision_id, metric, series_key, interval_start)` для истории, `(run_id, series_key, interval_start)` для прогнозов; географический индекс для геометрии. Партиционирование по времени — после замеров. Исходные миллионы строк обрабатываются пакетно, API получает агрегаты с ограниченным размером страницы.

Проверки конвейера: дубликаты, корректность времени и координат, ссылки на сеть нужной версии, доля несопоставленных записей, пропуски и неполные интервалы. Ошибки отправляются в карантин с причиной, реальные всплески сохраняются. Публиковать новую версию можно только после проверок; предыдущая остаётся доступной.

4. **G3 — готово к сдаче:** проект поднимается по инструкции, проверки воспроизводятся, демонстрация и презентация соответствуют измеренным результатам.

## 7. Реализация прогнозирования

Для реконструкции наполненности до прогнозирования реализуется [баланс групп пассажиров](docs/PASSENGER_OCCUPANCY.md). Сначала — проверяемая эвристика без обучения и сохранение остатка; затем независимая оценка ошибки. География метро/хабов, погода и события подключаются по [правилам источников](docs/DATA_SOURCES.md). Число событий и близость пересадки не преобразуются в пассажиров произвольным коэффициентом без проверки.

1. У2 формирует целевые ряды с учётом расписания работы, полноты источника и изменений сети. Закрытый маршрут, нулевой спрос и сбой поступления данных различаются.
2. У3 заранее фиксирует даты folds, основную метрику и правило определения пиков. Даты и маршруты теста не подбираются после просмотра качества.
3. Рассчитываются сезонные базовые прогнозы: соответствующий час/день прошлой недели для коротких периодов, сезонные месяцы прошлых лет для длинных, если история позволяет. Для каждого профиля сохраняется точное правило базы.
4. Добавляется простая регрессия, затем модель-кандидат с лагами, скользящими статистиками и календарём. Лаги строятся только из доступного прошлого. При рекурсивном прогнозе будущие факты не подставляются; способ прогноза сохраняется в версии модели.
5. Для каждого горизонта используется прямой прогноз или отдельная модель на его шаге. Если годовая детализация месячная, оценка проводится по полным месячным точкам. Не складывать независимо рассчитанные часовые значения для изображения точности годового прогноза.
6. Подбор параметров — внутри обучающей части; оценка — на последующих полных горизонтах. Скалеры, кодировщики и восстановление пропусков обучаются заново внутри fold.
7. MAE считается в единицах показателя. `WAPE = sum(abs(y - y_hat)) / sum(y)` передаётся как доля; при нулевой сумме факта значение `null` с причиной. Отдельно публикуются число точек, покрытие, пропуски, результаты по маршрутам и пикам.
8. Модель публикуется с manifest: код, версия данных и признаков, границы обучения, параметры, seed, профили и метрики. Отсутствие улучшения относительно базы фиксируется; до улучшения допускается честно названный базовый прогноз.

Для P1 добавить диапазоны: оценить их на отложенных периодах, сохранять нижнюю/верхнюю границу, номинальное покрытие, фактическое покрытие и среднюю ширину. Если диапазон недоступен, `prediction_interval: null`. Будущая фактическая погода не используется; долговременные изменения инфраструктуры оформляются как отдельные сценарии.

### Согласованность и обновление

- При открытии UI получает `/data-status`, фиксирует `dataset_revision_id`, затем capabilities и справочники этой версии. Версии данных и сети не смешиваются между страницами.
- Карта и график используют один `run_id`, пространственные фильтры и временные границы. `/map` выбирает точный сохранённый интервал, без повторного расчёта и скрытой агрегации. При отсутствии геометрии объект имеет `geometry: null` и предупреждение.
- В каждой точке происхождение (`observed`, `estimated`, `forecast`) отделено от режима источника (`live`, `batch`, `replay`, `demo`): прогноз по демонстрационным данным остаётся прогнозом с меткой demo.
- Клиент запрашивает все страницы в рамках выбранного периода. Курсор связан с версией и фильтрами; смена фильтра со старым курсором — 400. Список ограничен 1000 точками на страницу, обрезание без `next_cursor` запрещено.
- Задание: `queued → running → succeeded | failed`. Результаты видимы только после атомарного перехода в `succeeded`. До этого чтение точек — 409 `RESULT_NOT_READY`.
- `Idempotency-Key` обязателен для POST: одинаковое тело и ключ у одного пользователя возвращают тот же запуск; другое тело — 409. Запись ключа и задание создаются в одной транзакции. Ключ хранится минимум 24 часа; после истечения возможен новый запуск.
- Для P0 — опрос статуса с `Retry-After`; UI прекращает его при завершении. `/data-status` возвращает рекомендуемый интервал опроса. Ошибки 429/503 повторяются с задержкой. Новую опубликованную версию UI показывает пользователю и согласованно переключает карту и график.
- Replay не означает живой поток. Поля времени источника и загрузки показываются раздельно, чтобы быстрая загрузка старой истории не выглядела свежими данными.

### Доступ и ошибки

Для первого закрытого стенда предлагается Bearer-токен из конфигурации с правами `viewer`/`operator`; запуск расчёта разрешён operator. Выдача токенов, регистрация и пароли не входят в P0. Для эксплуатации подключается принятый в организации механизм доступа. `/health` публичен и не раскрывает секретов.

Ошибки имеют единый JSON: `code`, `message`, `request_id`, `details`. Исключение — `/health`, где 503 сохраняет схему состояния готовности. Невалидные сочетания фильтров — 422; неизвестный ресурс — 404; курсор — 400; конфликт/неготовый результат — 409; ограничение частоты — 429; временная недоступность — 503. Стек вызовов и идентификаторы пассажиров клиенту не выдаются.

## 9. Проверки и критерии готовности

| Область | Проверка | Критерий |
| --- | --- | --- |
| Данные | Повторный импорт одного manifest | Те же агрегаты и контрольные суммы, нет дублей |
| География | Связь точки с действующей версией маршрута и позицией остановки | Нет молчаливой привязки к другой версии; несопоставленные записи отражены в аудите |
| Время | Границы суток/месяца/года, 31 января, високосный год, смещения RFC 3339 | Нет двойного счёта и неверной длины периода |
| ML | Временные folds для дня, месяца и года | Полный горизонт после обучающей части; известны MAE/WAPE и качество баз |
| Утечки | Лаги, подбор модели, внешние `available_at` | Для каждой точки не использовано неизвестное на `as_of` |
| Контракт | OpenAPI-валидатор и проверка ответов по схемам | Валидная схема, примеры соответствуют типам, реализация совместима с YAML |
| Фильтры | Маршрут/направление/остановка/участок, неверные сочетания | Правильная выборка либо описанная 422; неподдерживаемые уровни не подменяются |
| Задания | Повтор POST, падение worker, повторная обработка | Один эффект на ключ, восстановление по lease, нет частично опубликованных данных |
| Карта/график | Один `run_id` и одинаковые фильтры | Совпадающие точки, единицы и период |
| UI | Пусто, загрузка, ошибка, устарело, demo/replay, `null` | Состояние понятно; отсутствие данных не отображается нулём |
| Производительность | Репрезентативный импорт и API под согласованной нагрузкой | Измерены память/время импорта, p50/p95 API и открытия экрана; пороги согласованы после первого прогона |
| Развёртывание | Запуск по README в чистом окружении | Миграции, импорт примера, расчёт и UI воспроизводятся |

Предварительный инженерный ориентир для обсуждения: p95 чтения готовых данных до 1 секунды, первый полезный экран до 3 секунд на согласованном стенде. Это не подтверждённый SLA. Измерения должны указывать железо, число маршрутов/записей, фильтры и параллелизм.

Связь с P0 исходной спецификации: F01 — этап 2; F02/F07 — этап 4; F03/F04/F05 — этапы 5–6; F06 — задания и обновление на этапах 5–7. Отсутствие исходных данных не снимает обязательное требование, а оставляет соответствующий пункт открытым.

## 12. Как открыть Swagger

`openapi.yaml` — самостоятельный контракт. HTTP-сервер теперь реализован: запуск `python -m tram.cli serve`, Swagger на `http://127.0.0.1:8000/docs`. Предварительная настройка описана в [README](README.md). Ниже сохранён альтернативный способ просмотра YAML через отдельный Swagger UI.

При установленном и запущенном Docker Desktop выполнить в PowerShell:

```powershell
docker run --rm --name tram-swagger -p 127.0.0.1:8081:8080 --mount "type=bind,source=C:\proga\projects\tram-ridership-prediction\openapi.yaml,target=/spec/openapi.yaml,readonly" -e SWAGGER_JSON=/spec/openapi.yaml docker.swagger.io/swaggerapi/swagger-ui
```

Открыть `http://localhost:8081`. Для `Try it out` нужен реализованный API на `http://localhost:8000/api/v1`, действующий токен и разрешённый origin Swagger UI. При реализации API опубликовать документацию на `/docs` и сохранить согласованность генерируемой схемы с контрактом. FastAPI поддерживает OpenAPI и встроенный Swagger UI: [документация FastAPI](https://fastapi.tiangolo.com/features/).

Формат контракта: [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0.html). Команда локального просмотра основана на [инструкции Swagger UI для Docker](https://swagger.io/docs/open-source-tools/swagger-ui/usage/installation/).
