# ИИ-прогноз загрузки трамвайных маршрутов

Исследовательская система для прогноза пассажиропотока и прототип backend API. Проект содержит FastAPI, PostgreSQL, отдельный worker и ML-код. Цель конкурсной модели — общий поток по маршруту и часу; текущие файлы не доказывают возможность достоверно оценить посадку/высадку на каждой остановке.

## С чего начать

1. Открой [план готовности к хакатону](docs/HACKATHON_READINESS_PLAN.md) — он соединяет требования PDF, ответы организаторов, фактическое состояние репозитория и источники данных.
2. Перейди в [план задач модели и backend](docs/ML_BACKEND_TASKS.md) и выполняй задачи по ID по порядку: подтверждение конкурсного набора → аудит → baseline/валидация → внешние признаки → модельный адаптер → backend review.
3. Для текущих инструкций окружения и запуска используй [локальную установку](docs/LOCAL_SETUP.md) и [операционные команды](docs/OPERATIONS.md).
4. Папки и файлы описаны в [карте репозитория](docs/FILE_MAP.md); состояние реализации и ограничения — в [STATUS](docs/STATUS.md).

## Что уже находится в коде

- Backend: FastAPI, SQLAlchemy/PostgreSQL, OpenAPI, очереди и worker, прогнозный `Predictor` port. Текущая сборка worker использует `SeasonalNaive`; обученная модель из `ml/training/train_tram.py` к HTTP прогнозу пока не подключена.
- Трамвайный конкурсный эксперимент: [`ml/training/train_tram.py`](ml/training/train_tram.py) создаёт route × date × hour прогноз и submission CSV. В `ml/predictions/submission.csv` имеется заголовок `route;date;hour;prediction` и 14 640 строк данных. Проверка числа строк не подтверждает качество, полноту ключей или отправку на площадку.
- Отдельный эксперимент метро: `ml/training/prepare.py`, `train.py`, `evaluate.py` обрабатывают квартальные данные из наборов Москвы 624/62743. Это другая целевая переменная и частота; она не является обучающей разметкой трамвая.
- Подготовленные наборы 624 и 62743, образцы погоды и KudaGo описаны в [реестре данных](docs/DATASETS.md), [аудите](docs/DATA_AUDIT.md) и в [sources/README.md](sources/README.md). Трамвайные конкурсные исходники в Git не подтверждены: `dataset/` игнорируется, поэтому сначала проверь локальную папку и скачай оригинал из [ссылки организаторов](https://disk.yandex.ru/d/DiFwlfMOauxjBg).
- В репозитории есть корневой `requirements.txt` и отдельный [`ml/training/requirements-gpu.txt`](ml/training/requirements-gpu.txt). План предусматривает сведение зависимостей к одной поддерживаемой инструкции и optional extras в `pyproject.toml`; не считать существующие два файла полностью синхронными.

## Что делать с внешними данными

Дополнительные источники дают признаки, но не заменяют метки целевого ряда. Наиболее полезные кандидаты: почасовой архив погоды Open-Meteo и официальный календарь РФ с переносами выходных. В плане описаны исторический архив и архивы именно выпущенных прогнозов погоды. Трафик Москвы и архив событий — условные источники: наличие живой страницы/API или текущего события ещё не подтверждает историческое покрытие для обучения. Каждый источник надо сверить по периоду, доступности на момент прогноза, лицензии и provenance, затем оценить отдельной временной абляцией.

Организаторы подтвердили, что `bus_stop_no` не даёт надёжного соответствия валидации остановке, а остановочная детализация опциональна. Поэтому конкурсная модель не должна создавать псевдоточность; основной результат — общий поток по маршруту. Маршрут 5 остаётся в сабмите: в ответах организатора разрешены нули или виртуальный прогноз.

## Обучение, оценка и backend

Текущая конкурсная модель — исследовательский код, а не подключённый backend model. Сначала нужно подтвердить входные CSV, значение нулей/пропусков, ключи теста и локальную реализацию WAPE-score; затем провести временную валидацию без утечки и проверить все ручные коэффициенты. Не использовать test для выбора модели и не считать проценты из старой документации подтверждённым результатом без сохранённых predictions/конфига и receipt платформы.

Дальнейшие пункты: версионированный model artifact с provenance и схемой признаков; единая трансформация для train и inference; адаптер к существующему `Predictor`; сезонный fallback; тесты API/inference; реальный benchmark backend. Обучение должно выполняться отдельной CLI/job-командой, а HTTP API — только инференс. Конкретные критерии и review для каждого этапа — в [ML_BACKEND_TASKS.md](docs/ML_BACKEND_TASKS.md).

## Локальный запуск

Из корня репозитория на Windows/PowerShell:

```powershell
py -3.12 -m venv .venv
```

При открытии нового терминала активируй окружение:

```powershell
.\.venv\Scripts\Activate.ps1
```

Затем отдельно установи зависимости и пакет:

```powershell
python -m pip install -r requirements.txt -e .
```

Создание `.venv` — одноразовый шаг; активацию нужно выполнять для каждого нового терминала. Полная инструкция с PostgreSQL, конфигурацией, проверками и запуском API/worker находится в [LOCAL_SETUP.md](docs/LOCAL_SETUP.md). Swagger после старта API: `http://127.0.0.1:8000/docs`.
